# B42 — One refresh session per user: two devices will keep signing each other out

| | |
|---|---|
| Severity | Medium (latent: it bites as soon as the frontend uses refresh tokens with a short `JWT_EXPIRES_IN`) |
| Area | Auth: refresh tokens (backend) |
| Status | Open, found 2026-10-06 |
| Where | `backend/src/modules/auth/token.service.ts` (`issue`, `rotate`), `users.refresh_token_hash` (migration `20261005000001`) |

## The bug

Each user has a single column, `users.refresh_token_hash`, holding the hash of their one valid
refresh token. Every `issue()` (login, social login, register, reset, password change) and every
`rotate()` (`POST /auth/refresh`) **overwrites** it.

`docs/REFRESH_TOKEN_AUTH.md` notes this as a limitation. It becomes a user-facing bug once the
planned follow-up lands (frontend refresh plus `JWT_EXPIRES_IN=15m`):

1. Anh is logged in on a laptop (refresh token R1) and a phone (R2). The phone's login replaced R1,
   so the laptop is already on borrowed time.
2. 15 minutes later the laptop's access token expires. It calls `/auth/refresh` with R1. The hash is
   R2's, so the conditional `UPDATE` matches 0 rows, the API returns 401, and the laptop logs out.
3. Anh logs in again on the laptop (R3). Now the phone's R2 is dead, and the phone logs out at its
   next refresh.

The user is bounced between devices every access-token lifetime. Customers who order on their
phone while the store owner keeps the console open on a PC will hit this every day.

## Why it matters now

The backend was built and verified this way on 2026-10-05, and the frontend follow-up (steps 1–5
in the doc) is next. Changing the storage model after clients depend on it is harder than doing it
before.

## Suggested fix

Store one row per session instead of one column per user:

```sql
CREATE TABLE refresh_sessions (
  id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id     BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_hash  VARCHAR(64) NOT NULL UNIQUE,
  user_agent  VARCHAR(255),
  expires_at  TIMESTAMPTZ NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_used_at TIMESTAMPTZ
);
```

- `issue`: insert a row (optionally cap at ~10 sessions per user, dropping the oldest).
- `rotate`: `UPDATE refresh_sessions SET token_hash = :new WHERE token_hash = :old AND expires_at > now()`.
  Same single-use guarantee, but only for this device.
- `revokeToken` (logout): delete that row. `revokeUser` (suspend, password change): delete all rows
  for the user.
- Bonus: an "Active sessions" list on the account page becomes possible.
